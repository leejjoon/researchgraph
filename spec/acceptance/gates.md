# Conditional activation gates

These scenarios apply through every operation door and with the index kept
and deleted. Generated nodes use their own normalised immutable fields.

1. Given a claimable Work type with a boolean `review` property and an activate gate with `when_fields: {review: true}`. When a Work is proposed with `review: true`. Then it is proposed, appears in queue, is not ready, and claim raises `not_ready` without changing files or approvals. After a permitted approval it is active and ready.
2. Given the same gate. When Work nodes are proposed with `review: false` and with review absent and no default. Then both are active, absent from queue, and claimable without approval.
3. Given review defaults to true. When review is omitted or supplied as null. Then defaults materialise before matching, stored review is true and the node is proposed. Given review defaults to false, omission instead creates an active node.
4. Given a gate with two conditions. When only one field matches, or either is missing. Then the gate does not match. When both match exactly, it does. A string `"1"` does not match number 1 and boolean true does not match number 1, even if a field schema permits either value. No values are coerced.
5. Given unconditional gates with absent `when_fields`, or an empty mapping on a concrete type. When a node of that type is created. Then the gate matches as before. Bundled research and tasks profiles retain their existing statuses and permissions.
6. Given two matching gates requiring owner and reviewer respectively. When owner approves. Then the record is appended but the node remains proposed and queued. When a different actor with reviewer role approves. Then it becomes active. A single approval satisfying both gates may activate it. A nonmatching gate cannot prevent activation or authorize an approval.
7. Given a matching human-only gate. When an agent approves. Then `human_only_approval`, no files changed. Given a matching agent-enabled reviewer gate, an agent declaring reviewer may approve; an undeclared or nonmatching role gets `wrong_role`. An unmatched agent-enabled gate cannot admit an agent to the matching human-only gate.
8. Given a profile declaring conditions on an unknown or nested property key, wildcard gated type (including an empty condition mapping), non-mapping condition, or null/array/object condition value. When loaded through registration or an installed entry point. Then `schema`. Given run or complete transition, `unsupported_gate_transition` remains the refusal.
9. Given an approved Work whose review field is true. When superseded with review false. Then the old node retires, the active replacement has no inherited approvals, and old immutable fields remain true. When superseded with review true or with fields omitted so true is copied, the replacement is proposed and needs fresh approvals.
10. Given a Task gate matching `{kind: expansion}`. When expand creates a Task. Then the Task is proposed. Given a nonmatching condition it is active. Schema defaults are materialised before matching the generated fields.
11. Given an Instruction gate matching a direct property with a true default. When instruct creates an Instruction, or supersede creates its optional Instruction. Then that Instruction is proposed independently of its target or replacement. With a false default it is active. The replacement separately evaluates its own gates.
12. Given a Failure gate matching `{step: validation}`. When a holder fails a running Task with that step. Then the Task becomes failed and the generated Failure is proposed. With a different or missing step and no default the Failure is active. With a matching default it is proposed.
13. Given arbitrary valid constructor, field and approval sequences. When each write succeeds or fails. Then I1–I8 hold, all required matching gates precede activation, rebuilding the cache yields identical show/queue/ready results, and no condition data is added to node or approval record formats.
