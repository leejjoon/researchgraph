# v0.2 work list (ordered)

Each item: what to build, and **done when**. One commit per item, message prefixed with the id. Items marked **[spec]** change `spec/` and carry the decision record named in the item (017 onward), written before the spec text in the same commit. Items marked **[decide]** name a choice the maintainer confirms before the commit lands.

Drafted 2026-10-21 by a two-member committee (Claude Fable 5.1, Codex GPT-6-Astra) from the proposal's v0.2 row and Gate 2, the backlog, the three viewer mockups in `docs/design/`, and the two Gate 1 findings from the astroharness profile.

**Inventory rule.** A new `rg` subcommand's row in `spec/operations.md` and its entry in `docs/user-manual.md` land in the commit that implements the command, never earlier, so `tests/test_docs.py`'s coverage check stays green at every commit. Semantics and acceptance scenarios may land earlier. Server launchers (`rg mcp`, `rg serve`) are documented in a separate "Servers" table, outside the graph-operation inventory.

**Stack assumed** (decision 017; each **[decide]**): MCP over stdio with the official `mcp` Python SDK in an optional `mcp` extra; HTTP adapter and SSE on Starlette/Uvicorn declared as direct dependencies of an optional `viewer` extra; change events derived by polling the index's `content_hash` (the source generation) and diffing observed states, no file-watcher dependency; the viewer as one framework-free custom element `<research-graph>` in plain ES modules with no bundler, static files packaged in the wheel and served by `rg serve`; browser tests with Playwright in a `viewer` test extra on the CPython jobs only (as decision 016 did for the notebook). Core runtime dependencies are unchanged.

**Rules carried from AGENTS.md.** No runner, scheduler, scientific procedure or agent prompt in the core: the only text an agent receives from the server is the profile's `agent_guidance`, and the scripted session prompt lives under `examples/`. No profile or discipline name in server or viewer code; the viewer reads type names, gates and order from the project's profile. Every new graph operation has Python, CLI `--json` and MCP doors. I1–I8, the frozen `--json` shapes, canonical graph and archive bytes, and query parity after index deletion are preserved throughout.

**Scope.** In: MCP server with read/write marks and an essential preset; change events; viewer graph view, inspector, review queue and live monitoring; a bulk `graph` read; an operation registry; the two profile extensions below. Out (v0.3 or later): diff view, timeline scrubber, budget-burn charts, "since you last looked" digest, renderer plugin API and notebook previews, standalone app, profile migrations, Atlas exporter, hypotree adapter, layout persistence, FTS5, sharding, `export --bundle`, full historical reconstruction, `run`/`complete` gates, `unlink`, sidecar event log, signed approvals and role files, reference enrichment (profile work). Mockup controls that depend on a consumer runner (runner capacity, lease or budget inheritance, instruction acknowledgement) are listed as deferred in decision 017.

- **T01 Profile contract for v0.2 [spec] [decide].** Decision 018, conditional activate gates: `Gate.when_fields: dict | None`, a conjunction of exact scalar matches against the node's normalised immutable `fields` (defaults materialised first); absent means unconditional; a missing field does not match; keys must be direct properties of the gated type's schema, else `schema` at load; `node_type="*"` with `when_fields` is refused at load; every matching gate must be satisfied; `run`/`complete` gates stay deferred per 009. Decision 019, citation targets: a profile may add target types to the core `cites` edge, keeping `Claim` as the only source and every existing pair; wildcards, narrowing and changes to any other core edge are refused with the existing `schema` error; `evidence`, `stale` and `weakest` are target-type-agnostic, with absent scoring fields treated as in `data-model.md` §8 and profiles that omit `Result` or `Reference` behaving as that table says. Spec text: `profiles.md` (Gate dataclass, load rules, endpoint rule), `data-model.md` (§2.3 "created `proposed` if an activate gate matches the node", §3 note on `cites`, §8 gate tuple gains `when_fields`), `operations.md` (`propose`: "or `active` if no activate gate matches"; `queue`: "`proposed` nodes matching at least one activate gate"). Acceptance: new `spec/acceptance/gates.md` (matching, non-matching and defaulted fields; roles and agents; every node-creating operation; supersession re-evaluates conditions and inherits no approvals; a matching node cannot be claimed before approval; no node-file or approval-record format change) and new scenarios in `link.md` and `propose.md` (profile-added `cites` target; removal and wildcard refused at load; existing `Reference` nodes stay valid; stored immutable types are never renamed). Done when records and spec changes are in one commit, `tests/test_docs.py` passes, and no code changes.
- **T02 Interface contract for v0.2 [spec] [decide].** Decision 017: the stack above; MCP in-package behind the `mcp` extra, one tool per operation with the CLI's names and arguments plus optional `now`, read/write annotations, server `instructions` = `agent_guidance`, actor fixed at launch (`--as-agent NAME` required unless `--as-human`), `--role` and `--read-only` honoured by the server and not overridable by tool arguments, errors as the CLI's JSON; HTTP adapter and viewer: `rg serve` on loopback with a launch token, `GET/POST /api/<op>` mirroring the CLI, `GET /api/operations`, `GET /api/events` as SSE, `GET /artifacts/<node>/<path>` under `artifacts/` only, Host and Origin checks, writes as the serving person's git identity with the role per request; the supported subset of the three mockups with every included control mapped to an existing operation or query and the deferred controls listed. Decision 020: `graph` read `{nodes: [...], edges: [...]}` including retired records, nodes and edges in `created, id` order, `--as-of` per `store-layout.md`; change events derived from differences between two observed states (`content_hash`, `history.jsonl`, HEAD and the clock), never from in-process hooks; envelopes `{seq, at, generation, commit, kind: index, counts, reset?}`, `{…, kind: node, change: created|updated, id, previous_status, node}`, `{…, kind: edge, change: created|retired, id, edge}`; `at` is the observation time and `commit` the observed HEAD, not provenance; cursor `(generation, seq)`; a cursor the source has not seen, a restart, or a disappeared record yields one `index` event with `reset: true` and the client refetches; coalescing, slow consumers and reconnect defined; time-derived state (lease expiry) refreshes without byte changes; `--no-commit` writes produce events; no persistent event file and no replay guarantee; rebuilds fabricate no domain events; a rebuild is never the sole change signal. Spec text: `store-layout.md` gains "Change events" under Index; `operations.md` gains a "Doors" paragraph (MCP and HTTP mirror the CLI; HTTP maps `RuleViolation` to 422 and project errors to 503), a "Streams" table header for `events`, and a "Servers" table header. Acceptance: new `graph.md`, `events.md` (external-process writes, HEAD changes, `--no-commit`, rollback and commit failure, same-second changes, cache deletion, restart, lease expiry, slow consumers), `mcp.md`, `serve.md`; `acceptance/README.md` says every scenario also passes through the MCP and HTTP doors once T09 and T11 land.
